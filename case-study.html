Separating real money from bot farms

A filtering system that scanned 800 public bounty listings, identified automated fraud farms, learned new ones on its own — and correctly concluded that the market was empty. Built and validated in one working session.

The problem

Public bounty boards advertise thousands of paid coding tasks. Most are worthless. Some are generated by bots on a schedule. Others are synthetic benchmark tasks planted inside forks of real projects. Many carry no funding at all. An automated system that trusts the listings burns its entire budget chasing bait — one decoy task ("Fix typo in README") had drawn 91 competing pull requests.

The hard part is not finding listings. It is rejecting them, and proving the rejection logic is sound rather than merely strict.

What the filter does

Checks run cheapest-first, so free signals from the search response eliminate most candidates before any rate-limited API call is spent:

  • Generated-title detection — an ISO timestamp inside an issue title means periodic generation, not a real problem.
  • Self-extending blocklist — when one repository emits many issues whose titles share a 25-character prefix, it is a generator. The system adds it permanently and without being told.
  • Repository integrity — forks (where synthetic benchmark tasks live), projects under 200 stars, repos younger than 90 days, maintainers inactive for 60+ days.
  • Proof of funding — a payment bot must have posted an actual dollar amount.
  • Already claimed — recent claim commands, a maintainer confirming a finalized pull request, or a maintainer asking people to stop submitting.

Proving the filter was not simply broken

A filter that rejects everything looks identical to a filter that works, if you only look at the output. Two checks separated them.

A control case. A synthetic clean listing — funded by a payment bot, no claims, active maintainer — must pass. It did, with the amount correctly extracted.

Manual verification of every survivor. All six funded bounties were inspected by hand. Every one was already taken: a finalized pull request pending review, competing pull requests disputing priority, or this, from a maintainer:

"please don't create any more PRs for this, there's already way too many of them"

The conclusion — that the market held no winnable work — was the correct output, not a malfunction. That finding redirected the entire project away from a dead end on day one.

A defect worth reporting

The first version searched only issues created in the last 120 days and rejected anything above 25 comments. It returned zero results from 101 candidates and looked like proof the market was empty. It was not: a live, funded $200 bounty open since June 2025 failed both rules.

Issue age was the wrong signal entirely. An old, funded, still-unclaimed bounty on an active project is a good target — it means the automated swarm tried and failed. The real death signal is an inactive maintainer. After the correction, the same scan surfaced six funded bounties instead of none.

Engineering notes

  • No LLM calls in the automated path. Scanning, filtering and scoring are deterministic code, so the scheduled job runs indefinitely at zero marginal cost. Judgment happens separately, out of the hot path.
  • Append-only ledger. Every action, cost and dead end is recorded and never rewritten, so any claim can be audited after the fact.
  • Rejection reasons are categories, not sentences. Embedding the star count in the reason string fragmented one pattern into dozens of rows and hid the signal.
  • Zero dependencies. Plain Node and a static page — nothing to install, nothing to break on a version bump.
